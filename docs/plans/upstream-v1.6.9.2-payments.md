# 官方 v1.6.9.2：支付模块合并记录

状态：PAY-01 至 PAY-14 已由用户逐项确认，候选已整合人工封顶审计、实测恢复、全部恢复的余额约束及启动支付包更新保护。未执行真实支付、数据库迁移或应用服务启动；当前候选仍有未解决冲突，数据库事务及真实路由验收未完成。

## PAY-01 / F-10：售卖策略与本地套餐

- 文件及调用链：`product-operations-page.tsx` → `services/api/payments.ts` → payment handler → `app/payment_products.go` → `repository/payment.go` → `models_payment.go`。购买经 `app/payment.go`，到账继续经过本地返利结算入口。
- 本地行为：保留商品卡片、权益、促销横幅、促销价格、站内购买、分级管理、兑换码及返利。
- 官方行为：新增不限量、周期、库存、定时四种单选策略，直接采用会覆盖部分本地字段及商品管理入口。
- 方案：排除新策略；或作为可选配置接入并保留本地业务。推荐后者。
- 最终决定：**全部可选策略接入，旧商品默认不限量。**策略编辑进入现有商品运营页，商品权限不并入支付渠道权限。
- 数据及权限影响：目录返回本地 `products/promotion/serverTime` 合同，并增加售卖状态；下单在商品锁内生成商品名称、最终金额和积分的订单快照，结算不按现价重算。积分保留本地两位小数规则。
- 验收：四种策略边界、促销开始/结束、库存并发、旧套餐展示、请求不接受客户端金额/积分、商品与财务管理员互不扩权。

## PAY-02：关单与库存释放

- 文件及调用链：用户/后台关单 → `app/payment.go:closePaymentOrder` → 渠道查询、关闭及复查 → `repository/payment.go:MarkPaymentOrderClosed`；后台补查位于 `payment_worker.go`。
- 本地行为：渠道不可查询或不支持关闭时仍可站内关闭，迟到的合法支付凭证继续到账。
- 官方行为：站内关闭即返还库存。
- 方案：立即释放；或区分站内关闭与渠道确认，推荐后者。
- 最终决定：**渠道确认未支付且关闭后释放库存；不明状态保留占用并补查。**
- 数据及权限影响：新增独立渠道确认时间，不从状态文案推断支付事实。释放与到账锁定同一订单，库存只释放一次。用户仅处理自己订单，后台继续使用支付订单权限。
- 验收：超时、关单与到账并发、重复关单、渠道已支付/已关闭、站内关闭后继续查单；未决占用不会因固定一天期限被遗忘。

## PAY-03：周期限购口径

- 文件及调用链：`CreatePaymentOrderWithProductReservation` 在商品锁内查询购买次数；后台补查未确认关单。
- 本地行为：此前没有周期策略；站内关单不代表渠道不能支付。
- 官方行为：按每用户、同商品、过去 N 天滚动计数，待付订单占名额，关闭释放。
- 方案：站内关闭释放；或渠道确认后释放，推荐后者。
- 最终决定：**滚动 N 天；待支付、下单结果不明及未确认关单都占名额，确认关闭后释放。**已到账订单继续计数，以订单创建时间落入窗口为准。
- 数据及权限影响：不把前端可购买状态当作逐用户配额证明；同商品下单串行复核，幂等重试返回原订单。
- 验收：同用户并发、防止先建多单后逐笔支付绕过、跨用户隔离、滚动边界、站内关闭保留和确认关闭释放。

## PAY-04：确认关闭后的迟到到账

- 文件及调用链：通知/查单 → `applyPaymentResult` → 本地 `completePaymentOrderWithReferral` → repository 事务。
- 本地行为：验签及订单金额、币种核对通过的迟到支付继续到账，原返利规则不变。
- 官方行为：确认关单释放库存后，原库存占用已不存在。
- 方案：拒绝到账或转人工；或按原快照到账并补记库存，推荐后者。
- 最终决定：**正常到账，补记库存消耗；超售时停用商品并记录异常。**
- 数据及权限影响：余额、订单、库存及异常审计同事务写入；重复凭证不重复加积分、返利或扣库存。超售保留负剩余库存供核对，不掩盖已支付事实。后台订单显示超售标记。
- 验收：释放后库存已被第二笔占用、迟到回调与查单并发、重复通知、超售商品停止售卖及后台核对。尚未新增退款功能。

## PAY-05：未决库存订单与策略切换

- 文件及调用链：商品运营保存 → `UpdateTopupProduct` → 商品锁及未决库存检查。
- 本地行为：名称、文案、促销等运营字段允许编辑。
- 官方行为：策略可切换，旧订单仍可能依赖库存状态。
- 方案：任意切换；或结清未决库存订单再切换，推荐后者。
- 最终决定：**库存未决订单结清前禁止切换策略；名称、文案和促销可继续编辑。**调整库存总量时不得低于已售加已占用；迟到支付造成超售时允许保持原库存总量编辑文案。
- 数据及权限影响：保留历史库存计数，切换策略不抹掉旧订单的库存语义；后续重新启用库存时仍计算历史消耗。
- 验收：有占用时拒绝切换，确认关单后允许；并发下单/返还不被商品保存覆盖；补库存及超售文案编辑。

## PAY-06：明确未创建与状态不明

- 文件及调用链：下单配置预检 → 创建订单并占用 → 渠道下单；关单走查询、关闭、复查。
- 本地行为：下单失败可能只是响应丢失，渠道实际已创建订单。
- 官方行为：失败或关闭路径可能返还库存，不能覆盖本地对模糊状态的保护。
- 方案：所有失败均释放；所有失败均保留；或只释放明确未创建，推荐第三种。
- 最终决定：**尚未调用渠道的配置错误不占用；查询、关单、复查均明确返回类型化“订单不存在”时允许释放；其他情况继续保留。**
- 数据及权限影响：解密、回调根地址及渠道配置校验在库存占用之前完成；普通网络错误不能被当作无单。三次明确无单经同一确认关闭事务释放名额和库存。
- 验收：预检失败没有订单/占用；三次无单释放一次；超时、两次无单加一次不明均不释放；复查发现已支付则正常到账。

## PAY-07：支付插件升级和卸载

- 文件及调用链：`protocol_registry.go:ensurePaymentPluginLifecycle/ensurePaymentPluginCanBeRemoved` → `ActivePaymentOrderCountForPlugin`。
- 当前行为：只把 created、pending、closing、create_failed 算未完成，站内关闭后可升级/卸载插件。
- 合并交叉：PAY-02/03 中部分 closed 订单仍占库存或周期名额，失去原插件会无法继续补查。
- 方案 A（推荐）：未确认且仍占库存或周期名额的订单同样阻止对应版本升级/插件卸载，结清后解除。
- 方案 B：维持原规则，本轮暂缓库存、周期策略。
- 数据及权限影响：A 不改变订单和权限，只延长插件变更保护；可能需要管理员先处理渠道长期不明的订单。
- 验收：未确认关单仍阻止变更；渠道确认关闭/已到账后解除；其他插件和版本不被误阻止。
- 最终决定：**未决占用结清前阻止升级和卸载，已整合候选。**库存占用必须结清；周期占用按当前商品配置和滚动窗口判断，窗口外不继续占名额。已有其他未支付状态继续受原有保护。
- 同版本替换不同包、替换包删除支付贡献同样不能绕过保护；原始包摘要相同的重复安装仍允许。新增后台回归覆盖未确认/已确认库存、周期窗口内外、同包重装及同版本替换，尚未运行。

## PAY-08：停用支付插件

- 文件及调用链：`plugin_management.go:SetPluginPlatformAvailability` → `SetPluginEnabled` → `protocol_plugins.go` 重建渠道注册表；历史订单通过该注册表查单、关单和验签。
- 双方当前行为：系统插件停用时同时停止其运行时，渠道从注册表移除。
- 合并交叉：库存/周期占用可能长期等待渠道确认；直接停用会同时失去存量订单处理能力。
- 方案 A（推荐）：停用支付插件只禁止新单并从购买渠道隐藏，继续保留存量订单查询、关闭及验签能力；升级和卸载仍按 PAY-07 拦截。
- 方案 B：有未结清订单时禁止停用，管理员改为单独关闭支付渠道的新单开关。
- 数据及权限影响：A 将平台可用性与支付运行时存在分开，既有后台权限不变；不会清除配置、订单或恢复新单。
- 验收：停用后普通用户不能新建订单、旧单仍可补查及到账；重启后效果一致，重新启用恢复新单；模型等其他插件行为保持原规则。
- 最终决定：**停用只停止新单、保留旧单处理，已整合候选。**平台可用性使用数据库开关，支付运行时继续启用，普通模型/应用的停用规则保留。新增暂停/恢复及历史查单回归用例，尚未运行；真实回调与重启仍待验收。

## PAY-09：结算金额精度

- 文件及调用链：任务报价/预授权 → `finance_billing.go:tokenUsageAmount/settleBillingOrder` → 余额和流水 → 钱包显示；与 `app/credit_cost.go`、前端报价有交叉。
- 本地行为：最终 Token 结算按 0.01 积分向上取整，账务展示与本地两位积分规则一致。
- 官方行为：保留到微积分，即 0.000001 积分；直接合入会改变扣费，例如计算值 0.001 积分从本地 0.01 变为 0.001。官方还新增音频及显式视频处理的实际时长结算分支，需要一起核对。
- 方案 A（推荐）：保留本地最终结算 0.01 积分粒度及向上取整，对采用的实际时长结算同样适配；供应商单位价格和中间计算保持必要精度。
- 方案 B：采用官方微积分结算，并同步修改前后端报价、余额/流水显示与相关合同，不重算历史账单。
- 数据及权限影响：影响新账单扣费金额，历史余额和订单不批量改写；新时长结算是否启用及超过授权上限的处理仍需核对调用链后单列讨论。
- 验收：零费用、粒度边界、预授权与实际金额一致、溢出、退款差额及 UI 显示；不得只修改显示或只修改 repository。
- 最终决定：**保留本地最终结算 0.01 积分粒度，已整合候选。**新增 `kernel.RoundCreditChargeUp`，报价、Token 预授权、Token 结算和采用的实测时长结算共同使用，供应商成本不按销售粒度取整。前端本地两位钱包展示与价格计算保留；已结算历史不重算。
- 实际 `credit_amount.go`、`token_billing.go` 及相邻测试文件专项：4 组、23 个子场景通过，另有合并用量后只取整一次的顶层用例通过。该命令不编译仍有冲突的 kernel 整包，也不测试数据库结算。

## PAY-10：音频与视频处理的实际时长结算

- 文件及调用链：`task_terminal.go` / 视频处理交付 → `task_billing.go` → `finance_billing.go:settleBillingOrder`；关联原报价、冻结积分、授权上限及待核对路径。
- 本地行为：按请求时长形成订单快照，完成后按原快照结算。普通视频生成仍应保持这条路径。
- 官方行为：按秒音频以及明确的视频处理任务采用真实输出时长，毫秒向上取整到秒；可能退回或补扣预授权差额。缺少时长时进入待核对。无显式授权上限的订单可能补扣超过原报价。
- 方案 A（推荐）：接入实测时长，默认以订单原报价为授权上限；更短则退差额，更长超过授权或时长未知时保留待核对，不自动超额补扣；已显式记录的授权上限继续执行。按 PAY-09 粒度结算，不重算已结算历史。
- 方案 B：本轮保留按请求时长的原快照结算，暂缓上述实际时长能力。
- 数据及权限影响：改变未结算的按秒媒体账单金额，不能只接 repository 分支；需同步交付、费用核对和前端提示。人工处理仍要求积分运营权限。
- 验收：输出不足/等于/超过请求、未知时长、向上取秒和 0.01 积分粒度、零授权、已有显式上限、按次音频及普通视频不受影响、重复交付不重复结算。
- 最终决定：**接入实测时长并保留授权上限。**自动结算默认使用原报价，已有显式授权（含零授权）继续生效；超出授权返回待核对错误，不改变资金。计算金额保留在待核对订单中，不代表已扣费。按次音频和普通视频生成保持原价快照，已结算订单重试不重算。
- 实现补充：毫秒向上取秒使用商和余数，避免加 999 溢出；按秒音频缺订单、缺实测接口或缺时长时拒绝降级为原价结算。计费结算、退款及恢复共用订单锁，避免同一订单并发重复记账。
- 初次计价时复用既有 `charge_limit_set/charge_limit_microcredits` 固化授权，防止切换供应线路后用新报价扩大上限；明确视频处理还按服务端准入标记补齐固化。线路切换与结算使用同一订单锁，较贵备用线路被拒绝，较便宜线路不能改掉原授权。
- 报价 API 新增可选 `settlementBasis: measured_duration` 和 `chargeLimitMicrocredits`（免费时显式为 0），并将对应报价标为 `estimated`。前端沿用 `http` 入口，直接系统音频也能查询报价；画布、模型选择器和创作等真实调用方共用报价说明，普通视频、按次音频和 Token 文案不混用。
- 新增 repository 授权矩阵 7 场景、时长边界 7 场景、按次音频/普通视频 2 场景及备用线路授权场景；任务交付 6 场景、实测能力缺失拒绝用例；报价 JSON 6 场景、授权固化 8 场景。上述数据库和 app 用例尚未运行，不能计为通过。
- `bun test test/model-quote.test.ts test/media-billing-quote.test.ts`：11 项、38 个断言通过，覆盖实际报价说明、原 Token 语义、真实 API 调用模块的路由/取消传递和实测零授权字段。报价说明拆为纯函数并由原模块再导出；未运行完整前端类型/构建或浏览器验收。
- 本批 12 个无冲突 Go 文件通过 gofmt 语法解析，4 个 TS 文件通过语法转换；`task_creation.go` 与 OpenAPI 仍有其他模块冲突，局部同步不会将它们标为全部已解决。

## PAY-11：超出授权后的人工结算

- 文件及调用链：后台积分运营 `resolveBillingOrder` → `SettleBilling`；当前人工结算不会重新读取媒体实际时长。
- 本地行为：人工核对有依据备注及管理员审计，按原订单快照结算。
- 官方交叉：按秒媒体要求实测；现在超授权必须待核对，直接调用普通结算会缺时长而失败。
- 方案 A（推荐）：后台人工结算重新核实实际时长；费用超授权时按原授权上限结算，差额由平台承担，并记录实测金额、授权、差额及操作依据，不能提高用户授权。缺时长继续拒绝，补齐依据或退款。
- 方案 B：这类超额单只允许退回预授权，不提供人工结算。
- 数据及权限影响：A 只在已有积分运营权限的明确人工操作生效；自动结算仍保留待核对。余额、账单、流水和差额审计须同步，不能只改按钮。
- 验收：未授权管理员拒绝、缺依据拒绝、人工上限不越权、实测差额审计、重复人工提交及与自动交付并发不重复扣费。
- 最终决定：**允许按原授权上限人工结算并审计，已整合候选。**读取任务所属用户的实际资源时长，核对任务与账单身份；按原授权封顶，资金、订单、核对人/依据及差额审计同事务提交。已结算重试不重复扣费或差额审计。缺时长、无权限或缺依据拒绝写入，普通 Token 结算规则保持。
- 审计保留实测金额、实扣、授权、平台承担差额、毫秒时长和操作者；供应商成本使用真实数量，不能把用户封顶价当成供应商成本。后台文案与操作按钮已同步。

## PAY-12：已退回订单后来确认生成成功

- 文件及调用链：`provider_task_recovery.go:settleRecoveredBilling` → `RestoreRefundedBillingOrder`。
- 本地行为：已退款后确认生成成功可恢复扣费；非 Token 订单按旧快照直接扣回，原路径未限制可用余额不能为负。
- 合并交叉：媒体改为按实测且受授权保护，恢复扣费不能绕开实测和上限，也不能把未知状态当作已获新授权。
- 方案 A（推荐）：保留恢复扣费能力；媒体同样按实测并受原授权和可用余额约束，超额、余额不足或缺时长时保留待核对，不直接按原价追扣。已结算订单不重算。
- 方案 B：已退款保持资金终态，恢复产物不自动追扣，另由人工处理。
- 数据及权限影响：影响恢复时余额和冻结状态；不能重复退款或重复补扣。按原快照恢复的其他计费路径也需核对余额不足时的行为，不能全局改变而不记录。
- 验收：退回后实测变短、超授权、余额不足、重复恢复及恢复/退款并发，资源可恢复但资金异常不被误报已结算。
- 最终决定：**保留恢复能力，媒体按实测且不越授权和余额；未知、超额或余额不足进入待核对，已整合候选。**新增 `refund_recovery_pending` 以区分已退回余额和仍冻结的预授权；恢复只从可用余额扣回，不碰其他任务冻结额；失败保留已退款事实。管理员取消恢复时只关闭核对，不再次增加余额。字段进入追加迁移清单，未执行迁移。

## PAY-13：非媒体退款恢复的负余额规则

- 文件及调用链：`finance_billing.go:RestoreRefundedBillingOrder`，相邻 `finance_recovery_test.go:TestRestoreRefundedBillingOrderUsesObservedTokenAmount`。
- 本地行为有明确测试：Token 退款后按实测用量恢复，即使可用余额不足也扣成负数（示例 100000 微积分扣回 1750000，预期余额为 -1650000）。按次恢复使用同一无余额约束的更新。
- 前项讨论明确采用媒体实测及余额约束；本项确定是否同时改变其他计费方式，避免把局部决定静默扩大。
- 方案 A（推荐）：所有退款后恢复均不得扣成负余额，不足进入退款恢复待核对；历史已结算账单及余额不重算。
- 方案 B：仅媒体采用余额约束，Token/按次保留本地原有允许负余额规则。
- 数据及权限影响：A 改变新的 Token/按次恢复行为，不清理历史欠款；B 保留旧欠款能力。不能只修改测试期望而不确认业务决定。
- 验收：媒体、Token、按次分别覆盖足额/不足额及重复恢复，不足额状态与余额/流水一致。
- 最终决定：**所有恢复都禁止扣成负余额，已整合候选。**Token 与按次恢复同样用原子余额条件，不足时进入退款恢复待核对；既有 Token 用量和授权规则保留。原明确期待负余额的测试已按决定修改为“余额不足保持原余额，补足后恢复一次”；不改写历史欠款或已结算账单。
