# DB-04：SQLite / PostgreSQL 转换入口

状态：用户已确认方案 1，候选实现及隔离验收完成。仅接受已验证的 Schema 83 离线副本，源只读、复制原账本、目标全程事务核对。未操作真实业务数据库，未启动候选应用。

## 冲突与调用链

- 编号：DB-04，对应最初 C-003。
- 文件：backend/cmd/migrate-sqlite-postgres/main.go；调用 main → verifySQLite / verifyMigrationCoverage → target.Transaction → database.MigrateSchema → migrations / migrateTable → 逐字段核对。
- 本地行为：只读 SQLite 源文件；新目标库先运行当前代码的 MigrateSchema，业务表逐个复制，不复制 schema_migrations。已有目标库只按业务表核对，账本未纳入同等核对。
- 官方行为：延续此转换流程，增加官方新表；自动合并仍遗漏本地和合并新增模型。该清单遗漏与转换流程已按本页最终决定修复。
- 与本轮批准边界的交叉：目标按新代码生成账本，会丢失源库原有谱系和 applied_at；不能把“目标结构创建成功”视为原历史保留。旧 Schema 51 也缺少本轮新表，不应按当前模型直接读取并靠零值猜新字段。
- 另一个代码证据：database.MigrateSchema 内迁移 25 会向空目标初始化 22 项精选灵感；migrateTable 随后对源数据使用 CreateInBatches，不会自动处理已有种子与原内容的冲突。现已通过完整转库用例覆盖目标种子与源内容相同身份、运营修改内容及源已删除默认条目三类情况。

## 方案

1. 用户已采用：本轮修复，转换入口仅接受已在副本升级并 verify 到 Schema 83 的 SQLite；源始终只读。新 PostgreSQL 目标必须为空，在同一事务处理结构、默认种子与全量复制，完整保留源的迁移名称、编号、校验和和执行时间。默认种子须精确识别后处理，不能用全表忽略冲突掩盖差异。非空目标仅在账本、结构和数据全部一致时返回幂等成功，不补写或覆盖。旧 51 先复制再升级副本，不能自动写原文件。
2. 本轮暂停转换功能：保留原转换代码供后续修复，但候选入口明确拒绝执行，提示使用原数据库部署；本轮只交付同数据库类型的 Schema 83 升级。另行安排跨库专题。
3. 扩展为直接接受 51 并转换升级：需要专门设计旧结构复制、事务内追加迁移和转换顺序；范围更大，不能据现有两个用例计为支持。

## 数据与权限影响

任何方案都不新增数据库迁移号，不改变已批准的 52–83。转换不接触生产数据库，不推送或部署。后续测试只使用原提交生成的虚构夹具和独立 PostgreSQL。管理员授权、资金与冻结、兑换码、返利、个人提示词、反馈/画布资源引用均必须纳入跨库比对；日志不得输出敏感正文或密钥。

## 验收

本地优先与官方优先两套源历史均需完整复制后核对账本和业务字段；覆盖权限/策展清单、复合主键、资源外键顺序、种子相同/不同、已有目标只读核对、拒绝旧源与异常账本、任一表失败整笔回滚，以及重复执行。原 SQLite 文件应保持逐字节不变。现有 database 历史升级夹具不是跨库转换验证。

最终决定：采用方案 1。原 51 副本先按已确认的 52–83 追加升级并 verify，然后才允许转换；不支持在转换入口直接从 51 升级。


## 最终实现

- main.go 保留环境变量入口与完整表清单，conversion.go 负责副本和事务；copy_rows.go 流式复制实际列、每批 100 行，并按主键顺序构建逐列摘要；schema_contract.go 核对列类型/长度/空值/默认值、主键、模型及关键部分索引、外键和新建自增序列。
- SQLite 使用编码后的只读 immutable URI，不创建读写连接或执行源迁移；拒绝尚有 WAL / journal 的副本。开始和提交前核对源文件 SHA-256，文件变化则中止目标事务。源存在未知表/列、视图/触发器、异常账本或无效外键时拒绝复制，不猜默认值。
- database.InitializeSchemaForCopy 只接受空表空间，运行真实迁移生成 DDL，再逐项验证本事务生成的灵感、策展根/设置、可读 ID 序列身份与数量；其他业务表必须为空。只删除这些新建默认行及新建账本，再复制源的全部原始行，避免覆盖已有运营内容。已有目标绝不调用初始化。
- 原迁移账本作为正式复制表，包括原编号、名称、校验和和 applied_at；PostgreSQL 按原时间的微秒精度保存，不重置为转换时间。业务软删除、SQL NULL、零值、二进制、序列化原文均保留，不触发模型默认值、时间和 BeforeCreate；Go 比较不以缺失字段零值掩盖差异。
- 非空目标必须结构、账本及所有持久化行一致，只读核对，不执行 AutoMigrate、种子清理、补写、可读 ID 序列推进。新目标的 PostgreSQL 自增序列在复制后校准，业务 id_sequences 原行不改。
- 不输出行正文、连接密码、API Key 或 PostgreSQL 错误详情；错误只报告表/列合同和 SQLSTATE。日志在事务成功提交后才报告完成。

## 验证结果

Linux Go 1.25.14 / GCC / CGO / PostgreSQL 17 隔离环境：

- 转库包 10 个顶层用例、35 项含子用例检查通过；新增实际可执行程序专项 1 组通过，真实编译并执行命令的旧源拒绝、完整转库及重复核对。
- database 包 88 个顶层用例、142 项含子用例检查通过，无跳过。新实例的初次联合回归曾因未重建 PostgreSQL 历史模板失败，补齐由原提交生成的四套夹具后联合回归通过；失败没有计为通过。
- 两套原 51 SQLite 夹具升级到 83 后完整转库，包含原账本、权限、配额、资金/冻结、兑换码、返利、提示词、软删除渠道/模型、二进制头像、工作台回执、灵感状态、归档反馈与画布引用。覆盖超过 100 行分批及大小写主键顺序；源文件哈希保持不变。
- PostgreSQL 强制只读连接重复核对通过；目标数据、执行时间、账本、表/视图/序列、字段类型/默认值/空值、索引唯一性/顺序/条件和外键异常均拒绝，不修复已有目标。
- 迟至复制结束的文件校验失败，以及后段字段长度异常，均验证目标 DDL、账本和业务行整笔回滚。异常错误不包含被拒绝的私有正文。
- 模型初始种子已编辑或删除时均保留源状态，不重新恢复默认内容；复制后的自增数值 ID 可以继续分配。

以上只包含虚构夹具。真实业务副本、完整 Backend、真实媒体访问与部署仍待总验收；资源物理对象及设置解密材料需按部署方案单独迁移。本轮未推送、发布或部署。
