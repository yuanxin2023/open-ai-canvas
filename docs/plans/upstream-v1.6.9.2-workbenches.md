## UI-02a：创建请求结果不明确，已确认采用方案 A

文件与调用链：`image-workbench-page.tsx` → `createWorkbenchTask` 或 `createGenerationTask` → `CreateWorkbenchTask` / `CreateTask` → 任务与计费事务。

固定本地基线与官方基线中，通用任务创建均没有供这两个新页面重放的公开请求身份；内部 Agent admission 的固定 ID 属于服务端能力，不能直接开放给浏览器。官方创建任务每次生成新 ID。POST 超时或丢失响应后，人工再次提交可能形成第二个任务及积分预授权；进程内的按钮锁不能覆盖刷新、重连或跨设备。

| 方案 | 行为 | 数据及权限影响 |
| --- | --- | --- |
| A，推荐 | 按账号持久记录一次提交的身份及请求摘要。重试相同请求返回原任务与原计价快照，不新增预授权；身份相同但参数不同拒绝。未知结果保留原身份继续核对，明确发起新任务才换身份。 | 需要前后端统一合同、事务唯一约束和确认后的追加迁移；不能持久化密钥或临时签名 URL。不能复用 Agent 私有 admission 绕过额度。 |
| B | 未知结果禁止再次提交同一操作，保留草稿与核对提示；人工查清后显式解锁并创建新请求。 | 本轮不新增去重账本，但需要持久保存账号内的待核对状态与人工确认规则；不能按“历史列表暂时没有”推断未接单。 |

最终决定：**用户确认相同请求重放原任务，避免重复预占；采用方案 A。** 不重算已存在的历史任务与账单。候选实现如下，真实事务与历史升级尚未验收：

- `workbench_submissions` 以 `(user_id, request_key)` 为复合主键，保存请求摘要、原任务 ID 和不可变报价。请求身份、任务、订单与积分预占在同一数据库事务提交；冲突插入只读取已提交的原记录，不再次执行任务/预占回调。准备阶段不写任务、不占款，不复用 Agent 私有 admission。
- 专用 POST 使用 `requestKey`；自定义渠道经通用 POST 使用 `workbenchRequestKey`，仅工作台任务接受该字段。服务端计算原请求摘要，TraceID/HTTP RequestID 不参与；参数不同返回 409 `workbench_submission_conflict`。
- 重放在新任务的开关、模型、价格和额度检查之前读取本人原回执；不触发新模型调用。响应的 `workbenchSubmission.quote` 固化原金额、计费模式、数量、价格版本和授权上限，不向普通用户增加供应成本或加价系数。原完整账单沿用既有不可变快照。
- 新页面同时携带期望账号，后端与登录身份复核；它不能授予身份或权限，用于拒绝请求发送期间 Cookie 切换带来的错账号写入。资源归属、配额、模型准入和本地 0.01 积分结算继续使用原写路径。
- 新请求身份限定独立工作台请求（不绑定画布项目），遵循既有工作台边界。首次接单记录活动/日志并唤醒调度，重放不重复这些动作。只有首次成功接单才固化报价；失败事务不消费标识，尚未接单的后续尝试仍走当前准入与报价。
- 前端在 POST 前用 IndexedDB 读改写事务原子保存账号/类型范围内的标识、摘要、端点和时间；不保存任务正文、密钥、签名地址或完整请求。此处只存小型去重元数据，跨窗口原子性由原生事务保证；任务、媒体与既有草稿存储继续使用原机制。保存失败就阻止发送。
- 未知结果保留标识。相同请求手动再次提交复用原标识；参数或端点改变时拒绝复用。刷新只恢复待确认身份，先通过只读 `GET /workbench/submissions/:requestKey` 核对，不自动 POST，也不声称恢复原草稿。若重填后不能重建相同请求（包括渠道配置或参考身份变化），继续核对或明确创建另一笔任务。
- “明确创建新任务”必须确认原任务仍可能完成计费，随后仅允许下一次手动提交使用新标识，不自动生成、取消或退款。旧标识留存在本机归档中；迟到回执不能清除另一笔新请求。成功详情读取不会覆盖原报价。
- 回执 GET 缺失返回 404 `workbench_submission_missing`，不据此推断原请求永远不会提交；原任务删除返回 410 `workbench_submission_task_removed`，服务端继续保留去重记录，禁止复用标识重新扣费。完整账号注销按原规则清理该账号回执。
- 新表登记到模型总表和账号清理链路。新增迁移候选依赖工作台任务分类与既有账单表，编号和校验和将在完整追加映射确认后制定；没有改写已部署迁移，没有执行真实迁移。

## UI-02b：历史重试改为载入参数，已确认采用方案 A

- 固定官方版本的调用链：`image-workbench-page.tsx.retryTask` → `retryGenerationTask` → `POST /tasks/:id/retry` → `taskLifecycle.retryTask` → `RetryTaskWithBilling`。该版本会立即调用此接口，复用原任务编号并建立新的计费订单；不经过两条创建入口的请求记录。
- 本地行为：既有任务中心的重试资格检查（包括费用、取消、审核与媒体恢复保护）继续保留。新工作台不能绕过这些规则，也不能因为创建接口已去重就宣称重试接口同样受保护。
- 方案 A，推荐：仅把新工作台历史入口改为载入可核实的原参数，让用户核对当前模型/报价并手动生成，走已确认的请求身份与事务路径。旧模型无法唯一定位或不可用时要求重选，不静默切换。保留旧任务、账单及媒体恢复、费用核对等保护，不改动其他任务中心的既有交互。
- 方案 B：保留点击后立即重试及同任务编号的体验，给这条独立重试接口另接请求身份、不可变报价及事务去重；不能简单把创建接口的账本声明套在其上。
- 数据及权限影响：A 明确形成另一笔手动提交并保留原历史，B 保留原任务的重试世代；两种均需校验本人、开关、模型、配额与费用资格，不自动退款，不绕过已有媒体的重试保存。
- 验收：费用/取消待核对与已生成媒体保护、加载失败不发送、模型不可用或多个同名渠道、参数复用、显式生成、超时重放与并发单次预占；其他本地任务中心继续按原规则。
- 最终决定：**用户确认方案 A：载入原参数，核对后手动生成。** 新工作台不再调用立即重试接口，历史按钮改为“载入原参数”；既有任务中心的交互保留，后端共享原重试资格检查及已确认的工作台关闭校验。
- 新增只读 `GET /workbench/tasks/:id/retry-intent`，仅返回本人独立工作台任务的安全参数、来源 ID 与版本。费用待核对、退款恢复待核对、取消待确认、内容审核、已生成媒体待保存，以及 Agent/智能创作审批任务继续拒绝普通重做；不在读取时排队或预占积分。
- 参数完整且素材可访问后才一次性更新编辑器；缺失规格、素材不可用、读取失败、草稿在等待期间被编辑、账号变化或请求被替代时保留当前内容。复用视频时长、画幅、分辨率和显式 false 值；旧规格与当前模型不一致时要求重新确认模型，避免隐藏改参造成报价与执行不一致。
- 自动模型恢复只认唯一公开逻辑模型身份或后端核实的自有渠道选择值，不按普通名称或分隔符外观猜渠道。旧身份缺失、不可用、重复或规格已变化时，清空本次选择并要求用户显式重选；此时选择器仅按能力展示模型，避免旧规格过滤掉所有可选项。供应路线和成本仍不公开。
- 手动提交携带 `retryOf/retryVersion`，自定义渠道对应 `workbenchRetryOf/workbenchRetryVersion`；必须使用 UI-02a 的请求身份。来源版本绑定本人、原任务/账单、状态、时间、提示词、模型和输入摘要等事实；来源变化返回 409 `workbench_retry_changed`，已接单的同请求仍先重放原回执。
- 提交前及数据库事务内复核资格。事务按原账单、钱包、新任务和来源任务的顺序处理锁，最终再次检查来源版本；失效则回滚新任务、账单、预占和请求记录，不唤醒生成。成功会创建另一条任务，保留原任务、账单和输入；来源关联写入经校验的任务元数据，客户端自填的保留关联键会被清除。
- 不新增数据表或迁移编号，复用 UI-02a 的提交回执表。真实 SQLite/PostgreSQL 事务、媒体保存入口和权限路由验收仍待完成，不把已补测试计为已通过。
